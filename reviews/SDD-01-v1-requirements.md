# SDD-01｜V1 需求冻结后的批判性评审

日期：2026-11-02  
范围：对 [SPEC.md](../SPEC.md) 的**需求与分析逻辑**做审查，不是代码测试。  
结论：**可作为 V1 开发需求基线；不可作为已完成作品集发布。**

## 评审原则
- 一个模块如果删掉不影响访客理解核心分析，优先删。
- 结论不能只靠故事连贯，必须能定位至 SQL 指标、观察口径和 Power BI 证据。
- 相关≠因果，历史复购≠未来流失，策略≠已验证效果。

## 本轮被否决的「看起来高级」做法
1. 全部四张 Power BI 重做成网页交互图表——重复投入，且容易出现统计口径不一致。
2. 首页摆上履约、收入、客户、支付四种 KPI——看着完整，但分散核心叙事。
3. 把「新客推动 GMV」写成已验证机制——缺少新老客收入拆解，不通过。
4. 把「流失客户」「流失率」作为历史 RFM 标签／3.04% 的正式名称——不能证明未来不复购，不通过。
5. 为了讲故事把配送延迟直接连接到历史复购率——无订单级、用户级对照分析，不通过。
6. 将策略建议改写为真实运营收益——没有实验，不通过。

## 最小开发顺序与闸门
**M1：首屏 + 主线信息结构** → 审查是否 60 秒能读懂、是否有暗示错误因果的文案。

**M2：主线证据入口** → 检查 SQL 对账、观察窗口、RFM 频次集中。

**M3：Power BI 原生嵌入** → 访客无账号真正可访问，确认模型公开安全。

**M4：履约侧证 + 方法折叠区** → 只留下可以复核的事实，未核验部分降级。

**M5：公开部署** → 检查访客可用、桌面／移动、键盘可达、Git 提交与所有链接。

每个 M 模块只有经「逻辑 + 证据 + 信息减法 + 功能测试」四项检查才允许标注完成。

## 最重要的未解决风险
- **数字对账尚未开始**：网页截图只是已见证据，不等于源数据 SQL 已通过一致性验证。
- **Power BI 发布权限未知**：微软 Public Publish to web 需满足授权与租户设置，且公开访问可能暴露语义模型底层数据；必须先做安全审查。
- **无新老客 GMV 拆分**：主线故意不宣称“增长靠拉新”，这不是漏洞而是严谨的边界。
- **没有真实经营干预结果**：网站必须展示策略假设和验证设计，不用杜撰 ROI。

**最终审判：需求基线 GO；网站上线 NO-GO。**
