# Olist 求职作品集｜第一轮批判性代码与业务审查

审查日期：2026-11-02  
审查对象：**本会话先前生成的 V3 本地版本**（`index.html`、`styles.css`、`app.js`、`config.js`、4 张 Power BI 截图及报告）。**不是当前 GitHub 网页**：本仓库在连接时是空仓库。  
目的：为未来上传到 Portfolio 仓库的正式版本设定审查门槛。未验证事项不得标注「已通过」。

## 一句话评语

**视觉设计成熟于分析论证**：V3 已做到简洁，但还不能让招聘方顺着「具体业务问题 → 可核验的指标 → 排除其他解释 → 可执行建议」完整检验能力。漂亮 ≠ 有说服力。

## P1｜明显影响招聘方理解效率

1. **项目最核心的决策未突出**。主标题「从交易增长追问用户价值与履约风险」能表达方向，但没有直接表明要决策什么。建议用「历史重复购买较少，优先验证首购后二次购买机会」作为核心主张，履约风险作为辅助案例。
2. **所谓分析流程仍偏通用**：`01 观察经营 → 02 识别问题 → 03 验证证据 → 04 提出实验` 几乎适用于任何 BI 项目。应把路径改成真实指标推导，例如「GMV 增长 → 按用户去重核对 94,983 → 购买频次中 96.96% 一次购 → Cohort 观察后续回购 → RFM 定义试验人群」。
3. **还缺一个关键对照分析**。由「月度 GMV 上升」不能推出「增长主要来自新客」；现有页面不应该暗示已经做过新老客收入贡献归因。若想以「增长质量」为核心，需要补算新老客 GMV 拆分。
4. **折叠的「方法」内容太浅**。`index.html` 写了 9 表、`customer_unique_id`、`SUM(price)`，却没有说明 order_items 和 reviews 关联重复计数如何避免；这恰恰最能体现 SQL 实践。
5. **Power BI 截图在手机端无法实际阅读**。V3 移动端图片缩小至容器宽度，中文和数值明显太小；正式嵌入也应有「全屏查看 / 打开报表」的可用入口。
6. **个人贡献和价值没有区分清楚**。应把「数据检查、口径设计、SQL 聚合、Power BI、策略设计」和「尚未实施的运营实验」分开，禁止把策略建议描述成已落地结果。

## P2｜工程质量和可访问性

- `case-tabs` 和 `report-tabs` 使用了 `role=tab`，但未实现完整的方向键切换、焦点管理和与各报表面板的一一对应；键盘交互应补足。
- iframe 仅检查 URL 形态 `https://app.powerbi.com/view`，并不等于链接能在未登录访客环境中加载。需端到端测试及失败提示。
- 样式内联式压缩严重，不便于审查与迭代；建议整理可读 CSS 和语义结构，避免未来改动产生隐性回归。
- 若把 V3 ZIP 中包含的 `.git/` 直接复制到现有远端仓库，会导致历史冲突；**仓库应以 GitHub main 为唯一上游，而不是推送旧 ZIP 自带的本地仓库历史**。

## 保留的优点

- 两个主题聚焦（用户复购、履约体验），优于上一版平铺四张看板。
- 用原生 Power BI 作为证据展示的方向正确，避免重复开发 ECharts。
- 对「历史复购 ≠ 流失概率」「延迟与低分 ≠ 已证实因果」的边界提示是加分项。
- `app.js` 的 Power BI URL 做了基本域名约束；不存在把任意外部 iframe 字符串直接注入的做法。

## 修改优先级与验收

**阶段 A：建立可信证据（优先）**  
目标：有三条可核验的 SQL、关键数字对账表、数据时间范围、可公开展示的 Power BI 链接或清晰未完成标识。

**阶段 B：精简业务故事**  
首页 1 句问题 + 1 条真实推导链 + 2 个独立核心案例；每个案例展示「问题 / 证据 / 结论 / 待验证假设」，不堆砌模块和 KPI。

**阶段 C：GitHub 与浏览器验收**  
经审查的网站代码推到该仓库；验证 PC、手机、未登录访客打开站点、报表跳转与 PDF / GitHub 链接。正式发布前不声称可公开查看原生交互报表。

## 本轮结论

**有条件保留 V3 的视觉设计和信息架构，但不应原封不动迁移部署。** 优先补证据，其次微调 UI；不要再通过增加装饰、动画或重复图表制造完成度。

> 本审查没有拿到新的 SQL 结果明细，也未获得真实 Power BI Service 嵌入 URL。所有待核验项必须保持「待核验」状态，不能将「没发现明显错误」当作「指标正确」。
