# Olist 作品集｜三项成果与证据说明

此文件用于解释网页上呈现的三项核心成果。项目使用 **Olist 巴西电商公开历史数据**，实际完成过 MySQL 查询、Jupyter EDA、Python 可视化及 Power BI 四页看板。不是平台真实业务运营报告，也不是流失预测模型。

## 01 · 四维商品收入一致性校验

**已保存的 Notebook 输出：** `eda.ipynb` 执行单元 16 展示：

| 汇总维度 | Notebook 汇总（R$） |
| --- | ---: |
| 月度（monthly_revenue） | 13,494,400.74 |
| 商品品类（category_revenue） | 13,494,400.739999998 |
| 用户 RFM（rfm_data） | 13,494,400.739999998 |
| 巴西州级（state_metrics） | 13,494,400.74 |

浮点型显示有微小精度尾差；统一保留两位小数后均为 **R$13,494,400.74**。这是四条分析路径的**商品价格金额汇总一致性**，不是对所有原始数据字段的全量正确性证明。

**体现的能力：**在不同业务粒度（商品明细、订单、用户、地区）间保持统计指标口径，并对多表关联的结果进行交叉核对。原查询使用 `SUM(order_items.price)`，**不包含运费**，也不等于支付总额或平台利润。

**可追溯材料：**[Notebook 执行记录](NOTEBOOK_EXECUTION_EVIDENCE.md)。原始 Notebook 保留在项目资料中，尚未上传公开仓库；不能声称读者可以从公开仓库立即独立重跑。

## 02 · 历史复购与用户分层

**Power BI 用户看板** [查看原始截图](../assets/03_customers.png) 显示：
- 历史购买用户数：**94,983**；
- 历史重复购买用户数：**2,887**；
- 历史复购率：**3.04%**；
- 一次购买用户数：**92,096（96.96%）**。

RFM 相关原始 EDA 在 `eda.ipynb` 中保存 **94,983 × 8** 的结果；Cohort 的原始 SQL 输出为 **120 × 5**。用户应按 `customer_unique_id` 去重，避免把交易层面的 `customer_id` 当作真实用户。

**业务解释：**历史样本中重复购买行为较少，值得进一步研究首购后二次购买机会；使用 Cohort 比较不同首购月份，RFM 辅助描述频次和消费分布。

**边界：**3.04% 是观察窗口内的历史复购，而非流失概率、未来留存率或同类行业对比结论；不同首购月份可观察时长不一样。此前作品集中部分 RFM 标签使用“Lost / Churned”，它只是规则分群名称，并非经模型验证的真实流失标签。

**技术证据：**[原分析笔记的执行记录](NOTEBOOK_EXECUTION_EVIDENCE.md)；另有 [新整理的复购 SQL](../sql/01_customer_repeat_purchase.sql) 和 [Cohort SQL](../sql/02_cohort_monthly_repeat.sql)，它们包含口径改进，**尚未在用户 MySQL 环境再次运行**，不能据此宣称与旧看板已完全一致。

## 03 · 配送时效与客户评分的关联

[Power BI 履约看板](../assets/04_fulfillment.png) 显示：
- 准时送达率：**93.23%**；
- 提前送达订单组平均评分约 **4.29**；
- 晚到 8 天及以上订单组平均评分约 **1.70**；
- 平均客户评分约 **4.09**（看板整体口径）。

原项目 Notebook 保存 **95,830 × 3** 的订单配送与评分明细（有评分样本）；另外有 **814 × 5** 的卖家表现排名结果。原始 SQL 对评价先按 `order_id` 求平均，并以 `DATEDIFF` 分组，对卖家指标使用 `DISTINCT seller_id, order_id` 处理一对多关联。

**业务解释：**严重延迟组的评价均值低于提前送达组，可优先分析严重延迟订单的分布及卖家履约情况。

**边界：**这是历史样本的分组相关性，不证明延迟*导致*差评，更没有真实实验验证整改收益。若要进一步比较不同配送分组，应检查各组订单数、实际有评分订单数和评分缺失比例；原 Notebook 的 95,830 行不可用来代替全部已妥投订单。

**技术证据：**[订单级延迟评分分析修订 SQL](../sql/03_delivery_review_by_delay.sql) 显式统计样本覆盖率，仍待在原数据库复跑。

## 前端展示规则

1. 首页只展示以上三个有来源的结果；看板图片保持 Power BI 原貌。
2. 四种收入汇总称为“口径一致性核对”，**不用“零误差”“彻底消除重复统计”** 等不可证明的夸张用语。
3. 指标区分 Notebook 已执行与 Power BI 已展示。新 SQL 修订版未复跑，不写成“新脚本复现成功”。
4. 没有原始 Notebook 公开、数据库来源和复跑记录前，不把 GitHub 仓库描述为完整的一键复现项目。
5. 后续如出现与截图数字不一致的新查询输出，先核对订单范围与时间窗口，不为保持视觉效果强行固定旧数值。
